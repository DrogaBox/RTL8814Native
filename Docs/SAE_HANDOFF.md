# WPA3-SAE: where it stands and what is left

Notes for whoever picks this up. Everything below was checked on my one setup (TP-Link Archer T9UH, macOS 26.7.1, OpenCore). Read `Docs/PHASE5_IO80211.md` (section "WPA3-SAE gates") first; this file is the to-do list that follows it.

## State

- Driver 4.22 and layer 0.30 are what is in my EFI right now. The layer is the 0.28 code plus three capability bits (`Source/AirLayer/RTLAirLayer.cpp`, `getCARD_CAPABILITIES`): `p[13] |= 0x08` (capability 75, SAE), `p[10] |= 0x10` (PMF), on top of the AWDL bits.
- With those bits macOS offers SAE on WPA3 networks, and `setWCL_ASSOCIATE` runs. For a WPA3-only hotspot it receives:
  - `key + 4` (key length) = the passphrase length, and the passphrase bytes at `key + 16`. For WPA2 it was always 32 (a PMK).
  - `req + 16` = 1 and `req + 20` = 0x1000 (open-system lower auth, SAE upper auth).
- In the deployed layer the join still fails because it only accepts a 32-byte PMK. The step 1 build below carries the passphrase but intentionally returns unsupported at the radio. `RTLAirLastAssoc` in ioreg keeps the header of the last request (no key bytes).
- Side effect: macOS now also tries SAE on my WPA2/WPA3 mixed router, and that join fails. Layer 0.28 (`Backups/airlayer_0.28`, md5 `7066099f...`) does not have the bits and keeps the router working. To go back, point `LAYER_SRC`/`LAYER_MD5` in `Tools/phase5_deploy.sh` at it and deploy.

## What the vendor code gives us

- `Source/rtl8814au/core/rtw_ieee80211.c` knows the SAE AKM selectors (00-0F-AC:8 and :9) and nothing more. There is no SAE logic in the vendor tree.
- `OnAuthClient` and `issue_auth` in `core/rtw_mlme_ext.c` are the places to hook the auth exchange. `OnAuthClient` has a cfg80211 branch for SAE that is not compiled here (we have no cfg80211). `issue_auth` always builds an open-system or shared-key frame, so SAE needs its own sender with algorithm 3 and an arbitrary body.
- `core/rtw_security.c` has BIP/IGTK code behind `CONFIG_IEEE80211W`. That flag is not set in `build.sh`. Turning it on has not been tried and may pull in files we do not build.
- `Source/Driver/WPA2Supplicant.c` is the in-kernel supplicant: self-contained SHA-1/HMAC-SHA1/PBKDF2, PRF-384, AES key unwrap, the 4-way handshake and the key install into the CAM. It only does AKM 2 (PSK) with key descriptor version 2.

## What has to be written

1. **Plumbing.** Done in ABI 2 and committed; the SAE branch still rejects the join until the exchange is connected. Preserve the passphrase wiping and WPA2 behavior described below.
2. **SAE exchange** (IEEE 802.11-2020, section 12.4): the standalone group-19 hunt-and-peck exchange is written and vector-tested below. It is not connected to the radio yet. Before using it, provide secure kernel entropy and review the timing and kernel-stack concerns noted below. The auth-frame TX/RX hook remains to be written; H2E is not implemented.
3. **RSN IE and association.** AKM 00-0F-AC:8, MFPC and MFPR set in the RSN capabilities (WPA3 requires PMF), and the right group management cipher.
4. **4-way handshake changes for AKM 8.** KDF-SHA256 for the PTK, AES-128-CMAC for the EAPOL-Key MIC (key descriptor version 3), and the IGTK in the key data of message 3.
5. **PMF in the data path.** BIP for group management frames, and protected unicast deauth/disassoc. The hardware may or may not help; this is the part I know least about.
6. **Join log entries** for each step so a failure can be located (`Source/Driver/RTLJoinLog.h`, read with `Tools/test_uc joinlog`).

### Step 1 — SAE passphrase plumbing (ABI 2; built, not deployed)

- `RTL_RADIO_ABI` is now 2. `rtl_radio_join` appends an SAE marker, a passphrase length, and a 63-byte passphrase buffer; the existing WPA2 PMK fields and offsets are unchanged.
- `setWCL_ASSOCIATE` recognizes upper auth `0x1000`, accepts a non-empty password up to 63 bytes, and copies it into the join request. It continues to treat a 32-byte key as a WPA2 PMK for non-SAE joins.
- `rtl8814native_radio_join` logs only the password length, calls the supplicant's SAE placeholder, wipes its local copy and the ABI request copy, then returns `-EOPNOTSUPP`. The placeholder resets security state and logs that SAE is not implemented. This is plumbing only; WPA3 joins still fail cleanly.
- The user-client temporary join structure is wiped after the call. No password bytes are logged or written to the join log.
- Verification: `./build.sh`, `./build_airlayer.sh`, and the `Tools/test_uc` compile completed; the required vendor-symbol grep returned no matches. No files under `Source/rtl8814au/os_dep/linux/` were built. Nothing has been deployed.

### Step 2 — standalone SAE group 19 (built, not connected)

- `Source/Driver/SAE.c` and `SAE.h` implement P-256 and legacy hunt-and-peck PWE derivation, SHA-256/HMAC and the SAE KDF without kernel headers or corecrypto imports. I started with hunt-and-peck because it is the first requested path; H2E is not implemented, so H2E-only access points will not work.
- The API prepares a commit, includes a supplied anti-clogging token in a retry without changing the commit, validates peer scalar/point and reflection, derives KCK/PMK/PMKID, and sends/verifies confirms with a saturating send counter and replay check. Authentication frames and the anti-clogging status/group are the responsibility of the future TX/RX hook. `finish` copies the PMK and PMKID only after confirm and wipes the exchange context; the caller must wipe the output buffers after use. `clear` wipes an abandoned exchange. No key bytes are logged by the module or test.
- The caller must supply a cryptographically secure entropy callback. **Do not use `rtl_get_random_bytes` for SAE:** its current xorshift/timebase implementation is not cryptographically secure. There is no kernel entropy callback wired up yet and the existing join path still rejects SAE.
- The PWE loop runs at least 40 rounds (up to 200 if necessary), uses masked first-candidate selection and switches to a random dummy password and identifier after finding it. The P-256 multiplication uses a fixed-length ladder and masked point selection. This is an attempt to reduce timing leakage, not a side-channel audit: the generated code and compiler behavior have not been independently reviewed. The partial stack measurements below do not yet bound total kernel stack usage. Hunt-and-peck itself has a history of side-channel attacks. Do not connect this to a production join path until those checks are done.
- Reference: the fixed group-19 vector in wpa_supplicant `src/common/common_module_tests.c`, branch `android10-qpr1-b-release`, labels its input IEEE P802.11-REVmd/D2.1 Annex J.10. The harness matches its local commit, KCK, PMK, PMKID and local confirm byte-for-byte and accepts its peer confirm. This is the vector as reproduced by wpa_supplicant, not an independent copy of the published 2020 standard. The test also checks a token retry, replay and invalid-input rejection, secret clearing and a two-party local exchange without password identifiers. It does not test a live hostapd session or the radio.
- Build and run the userland harness from the repository root:

  ```bash
  mkdir -p Build
  clang -DRTL_SAE_TESTING -std=c11 -Wall -Wextra -Werror -O2 -ISource/Driver \
      Source/Driver/SAE.c Tools/sae_test.c -o Build/sae_test
  ./Build/sae_test
  ```

  The deterministic scalar entry point is available only in the test build. The harness was also run with address and undefined-behavior sanitizers.
- `./build.sh` compiles the module into the kext without connecting it to the join path. The required unresolved vendor-symbol check was empty. `nm -u` on the SAE object showed only `memcpy` and `memset`; there are no corecrypto or extra arithmetic runtime imports. No `os_dep/linux` source was compiled and no deployment was performed.

### Step 3 — work in progress, not ready to deploy

- The latest scan found `internetXpete` on channel 149. The earlier raw scan showed SAE AKM, MFPC and MFPR, and H2E capability in RSNXE. The group management cipher was absent and therefore defaults to BIP-CMAC-128. The AP did not advertise the H2E-only membership selector; this does not prove it will accept hunt-and-peck.
- The standalone module now has an RSN IE builder for SAE/CCMP, a PMKID, MFPC, optional MFPR, and explicit BIP-CMAC-128. Its byte layout and bounds are tested in `Tools/sae_test.c`. It is not yet used in an association request.
- The management dispatcher records complete SAE auth frames from the target BSSID before duplicate filtering, with only the sequence and exact status. `Tools/test_uc joinlog` prints sequence 1 as commit and 2 as confirm, and labels status 126 H2E and 127 SAE-PK. Status values must be interpreted in the context of the exchange; neither value alone proves that the AP rejected hunt-and-peck. This logging has not been tested against a live SAE exchange.
- SAE join still returns `-EOPNOTSUPP`: no commit or confirm frame sender, receive state machine, token retry, secure entropy callback, SAE PMK handoff, association request, or 4-way boundary is connected. The join must remain disabled until worker execution, cancellation, teardown, retry timing, and key lifetime have been made safe. The current calculation is too expensive to perform on the shared RX workqueue.
- An unoptimized `-mkernel -fstack-usage` build and its direct-call disassembly give a maximum internal SAE chain of 3,560 bytes for start and 3,112 bytes for peer-commit processing. These figures exclude the random callback, external functions, the future caller, interrupts and other kernel overhead. A total kernel-stack bound and any necessary relocation of temporaries are still required.
- The kernel symbol inventory lists `_read_random`, and XNU's Mach KPI export list names it, but the current kext does not import it; its actual third-party binding has not been verified. The SAE object currently imports only `memcpy` and `memset`. Do not use `rtl_get_random_bytes` for SAE.
- Verification so far: the standalone SAE harness passed including the RSN IE cases; `./build.sh`, `./build_airlayer.sh`, and the diagnostic CLI compile succeeded. The required unresolved vendor-symbol grep was empty. The `nm -u` list is unchanged from the saved step 2 list: 530 imports, none new. A comparison with the saved 25.6.0 KC symbol dumps found ten existing imports absent from those incomplete dumps, so this is not proof that all imports resolve. `kextlibs -all-symbols` failed to find any library kexts on this system and could not verify them either. No `os_dep/linux` sources were compiled, and nothing was deployed or rebooted. This is not a completed step 3 build.

### Step 3, added: the SAE join itself (built, not deployed, not yet run against an AP)

- `Source/Driver/SAEJoin.c/.h` is the state machine. A new `rtl_sae_wq` thread in `Source/Compat/Compat.c` runs all of it: the join thread only stores the passphrase, the receive path only copies authentication frames into a four-slot ring, and the link timer only sets a flag, so no P-256 work runs on the RX worker or in a timer. The worker is the only owner of the exchange context. A generation counter drops anything left over from an earlier join, and `rtl_sae_join_cancel` (leave, any non-SAE join) bumps it and has the worker wipe its copy.
- Flow: `radio_join` (SAE) -> `rtl_sae_join_prepare` (checks the entropy source, stores the passphrase, gives `securitypriv` an RSN IE slot) -> `rtw_set_802_11_connect` -> `start_clnt_auth` posts the start instead of sending an open auth frame -> worker derives the password element, sends the commit -> peer commit (status 76 token retry, 77/126/127 and any other status end the join with that status) -> confirm -> peer confirm -> `rtl_sae_p256_finish` -> RSN IE with the PMKID, MFPC and MFPR as the AP requires -> `start_clnt_assoc`.
- Hooks in the vendor tree (all marked): `start_clnt_auth`, `OnAuthClient`, `link_timer_hdl`, `_issue_assocreq` (the RSN IE in the association request comes from SAE instead of the AP's copy).
- Join log: `JL_SAE_STEP` events (prepare, start, commit tx, token, peer commit, confirm tx, peer confirm, keys, assoc, retry, FAIL, stale, compute ms), printed by `test_uc joinlog`. Together with the existing SAE auth rx/tx events this shows where an exchange stopped and the exact status the AP sent. No key bytes are logged.
- The PMK and PMKID are kept in `g_sae` after the exchange for step 4 and wiped on cancel. Nothing uses them yet: `g_wpa2.active` stays 0, so the WPA2 handshake handler ignores the AP's EAPOL message 1, and the join will not complete. After association the AP will time the station out. That is the expected end of step 3.
- A wake re-join is disabled after an SAE join (`g_last_ssid` is cleared), since the passphrase is not kept and an open re-join would be wrong.
- Not tested: everything here is build-verified only. The hunt-and-peck compute time in the kernel is unmeasured (about 0.1 s per exchange in the userland harness). The worker has no timeout of its own besides the link timer retries (500 ms, 4 tries) and the join's overall watchdog. `rtl_sae_join_exit` wipes the worker's copy only if the worker still gets to run during unload.
- First live run (driver 4.23): the join reached the SAE worker on the real AP, then `start` failed in 0 ms. `rtl_sae_p256_start` asks the entropy callback for 254 bytes (the dummy password identifier) and `rtl_sae_entropy_fill` refused anything over 64 bytes; the userland harness has no such limit, so it never showed. The same run proved `_read_random` binds in the running kernel. Fixed in driver 4.23.1 (`Backups/build_4.23.1`, md5 `92599d00cf29ad1291f175049adabc6b`): long requests are served in 64-byte pieces.
- Second live run (4.23.1): `start` still failed in 0 ms, so entropy was not the whole story. The worker's start handler called `sae_wipe_worker()` first, which also erased the passphrase copy the start event had just filled, so `rtl_sae_p256_start` saw a zero-length password. Fixed in 4.23.2 (`Backups/build_4.23.2`, md5 `45df0ceebf494a1cb038733c0a65cfb6`) by splitting out `sae_drop_ctx()`. The userland harness cannot catch this kind of mistake because it never runs `SAEJoin.c`.
- Third live run (4.23.2) against the real hotspot: the whole SAE exchange worked. Commit sent, peer commit processed (about 350 ms), confirm exchanged and verified both ways, PMK and PMKID derived (`keys result=0`), so hunt-and-peck is accepted by this AP and the password matched. The join then failed only because `sae_complete` treated the 0 returned by `rtl_sae_build_rsn_ie` as a length. Also fixed the AP RSN parser, which started two bytes too far and would never have seen PMF-required. Driver 4.23.3 (`Backups/build_4.23.3`, md5 `613d9d9d9d4d88312f2a8d412e06778f`).\n- Builds: driver md5 `24732ed03947a414fe14c71bf0d80149` (`Backups/build_4.23`, superseded), layer 0.31 md5 `8558455c7b18623ae6ee50d19dd0e267` (`Backups/airlayer_0.31`, radio ABI 2). They must be deployed together.

### Step 4 — 4-way handshake for AKM 8 (built, not yet run against an AP)

- Fourth live run (driver 4.23.3): authentication and association both succeed against the hotspot. `assoc rx` status 0 and `join res` 1 follow `SAE step assoc` (RSN IE of 44 bytes). About four seconds later the AP sends a deauth with reason 15 (4-way handshake timeout), which is what a station that never answers message 1 gets.
- `SAE.c` gained two portable primitives, both tested in `Tools/sae_test.c`: `rtl_aes128_cmac` (the four examples of RFC 4493 pass) and `rtl_sae_derive_ptk` (KDF-SHA256 with the "Pairwise key expansion" label, 384 bits; checked against an independent Python implementation, and the result does not depend on which side is which).
- `WPA2Supplicant.c`: `rtl8814_wpa2_start_sae` arms the handshake with the SAE PMK and the exact RSN IE sent in the association request (it carries the PMKID). With `akm_sae` set, message 1 derives the PTK with KDF-SHA256, the SNonce comes from `rtl_sae_entropy_fill` (never the xorshift generator), and every EAPOL-Key MIC (sent and checked, including the group key handshake) is AES-128-CMAC. The key descriptor version is echoed from the AP, so both version 0 and version 3 work. The unwrap of the key data and the key install are unchanged. The GTK KDE is taken and the IGTK KDE is skipped.
- Because the supplicant state is now non-zero after SAE, the layer no longer reports `port 1` as soon as the radio is linked: the port opens only when the handshake completes.
- Not done: the IGTK is not installed and BIP is not handled (step 5). PMF is required by this AP, so protected unicast and group management frames may be dropped or mishandled after the handshake. Driver 4.24 (`Backups/build_4.24`, md5 `9eca28a115b051ed5341d3cf5c281eb8`).

### Step 3, added: kernel entropy source (built, not deployed)

- `rtl_sae_entropy_fill` (`Source/Compat/Compat.c`, declared in `Source/Compat/include/linux/random.h`) fills the `rtl_sae_random_fn` signature the SAE module expects: it calls XNU's kernel CSPRNG and returns 0, or -1 when the symbol did not bind or the request exceeds 64 bytes. The SAE join path still does not call it, so nothing changes at runtime yet.
- The `read_random` import is **weak** (`__attribute__((weak_import))`): `nm -mu` shows `(undefined) weak external _read_random (dynamically looked up)`. A kernel without the export still loads the driver (kxld binds the name to NULL) and the function returns failure, so SAE stays fail-closed instead of falling back to the xorshift PRNG. This removes the load-failure risk the earlier note worried about.
- Static evidence before the first deploy with this build: `_read_random` sits in the saved 25.6.0 KC inventories (`Docs/re/io80211_25.6.0/syms_com.apple.kernel.txt`, address `ffffff80004a8ce0`, flag `0f`) with the same export flag as KPIs this driver already binds (`_copyin`, `_vnode_put`), and XNU's Mach export list names it. The definitive proof is the first load of a build carrying the import: if `kextstat` shows the driver, the symbol bound; then `rtl_sae_entropy_fill` returns success. Verify on the next planned deploy/reboot (with the usual rollback ready).
- The stale comment in `linux/random.h` claiming `get_random_bytes` already used `read_random` was corrected: it is xorshift64* and must stay away from key material.

### Where to resume

The step 3 work is **uncommitted** in `Docs/SAE_HANDOFF.md`, `Source/Driver/RTLJoinLog.h`, `Source/Driver/SAE.c`, `Source/Driver/SAE.h`, `Source/rtl8814au/core/rtw_mlme_ext.c`, `Tools/sae_test.c` and `Tools/test_uc.c`. Check `git status` before making further changes. Do not discard these edits.
- The latest scan observed BSSID `46:81:62:24:40:20`, channel 149, SSID `internetXpete`. The raw IE bytes from the earlier inspection were not saved in the repository; rescan and capture them if exact bytes are needed. A later scan found the SSID again but did not dump its IEs.
- Authentication begins from the beacon receive path. `OnAuthClient` runs on the RX workqueue, while `link_timer_hdl` handles retries at `REAUTH_TO` (300 ms) and the association timer can end the join. The current vendor sender only builds open/shared auth. A safe integration needs algorithm 3 commit/confirm frames, group-19 and status-76 token handling, bounded frame parsing, and stale-response handling, all serialized against retry, cancellation and teardown.
- The compat layer has one system worker and one RX worker; `cancel_work_sync` flushes both queues rather than cancelling just one item. Do not put expensive P-256 work on the RX worker or wait for a global queue flush from a worker. A separate worker needs a lifetime and cancellation design that cannot use a freed adapter after leave, timeout, suspend or remove. The AirLayer's join poll can also retry and times out after 20 seconds; its cached SAE password is wiped and cannot be used for a retry.
- The ordinary RSN construction copies `securitypriv.supplicant_ie` into the join network before authentication. `rtw_rsn_sync_pmkid` can remove an unrecognized PMKID and contains key-format debug logging. Ensure the SAE PMKID and BIP cipher actually survive into the outgoing association request, without logging PMKID or other key material. Do not assume that the standalone IE builder alone changes the transmitted frame.
- Leave SAE fail-closed until the 4-way boundary and blocked port are demonstrably safe. In particular, do not feed SAE message 1 into the existing WPA2-PSK handler: it uses the WPA2 PRF, MIC and `rtl_get_random_bytes`. The SAE 4-way handshake and IGTK work belong to step 4, and protected management frames to step 5.
- `_read_random` appears in the saved 25.6.0 kernel symbol inventory and in XNU's [Mach export list](https://newosxbook.com/src.php?tree=xnu&file=/config/Mach.exports); its [declaration](https://newosxbook.com/src.php?tree=xnu&file=/bsd/sys/random.h) uses `void read_random(void *, u_int)`. The driver now imports it weakly (see the entropy subsection above); the remaining question — that the running kernel actually binds it for a third-party kext — is answered by the first load of such a build. The stock x86_64 XNU source has a nominal 16 KiB kernel stack in its normal default configuration, but this is not a measurement of remaining stack on this machine; see [XNU stack definitions](https://newosxbook.com/src.php?tree=xnu&file=/osfmk/mach/i386/vm_param.h).

## How I test

- A phone hotspot set to WPA3 (my router is locked, so I cannot force WPA3 or change its channel). The Wi-Fi password only ever goes into the macOS dialog, never into a command or a log.
- Build: `./build.sh` and `./build_airlayer.sh`; after the driver build `nm -u ... | grep -E "rtw|rtl|hal|dm_|odm|beam"` must print nothing. Never compile anything under `Source/rtl8814au/os_dep/linux/`.
